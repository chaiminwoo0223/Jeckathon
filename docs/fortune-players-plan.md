# 운세 v2 — 출전 선수 생년월일 + 6단계 길흉 시드 (확정)

브랜치: `ai/fortune-seed`. 담당: AI. 명세 정본: `docs/cheer101-spec.md` §2.12·§4.7 (결정이 바뀌면 명세를 먼저 고친다).

## 1. 목표

경기 당일 두 팀 선수들의 **생년월일**로 운세를 계산해, 팀 등급(대길·중길·소길·소흉·중흉·대흉)과 "오늘 기운 좋은 선수 3명 + 조심할 선수 1명"을 보여준다. 문구는 AI가 아니라 시드 데이터다(이름만 AI 운세). 결과는 같은 날 항상 같고, 네트워크 호출·DB 저장 결과 캐시는 없다.

## 2. 확정한 결정 (UX 근거 포함)

| # | 결정 | 이유 |
|---|---|---|
| 1 | 후보 선수 = `role=선수` 이면서 **등번호가 0~99**인 사람(팀당 60~72명). 3자리(육성)·등번호 없음 제외 | 데이터에 1군 구분·라인업이 없다. 팬이 모르는 2군 이름이 나오는 것을 줄이는 근사치. 1군 엔트리가 생기면 후보만 교체 |
| 2 | 화면은 **팀 등급(큰 글씨) → 선수 4명** 순서. 선수는 기운 좋은 3명 + 조심할 1명 | 100명 목록은 읽지 않는다. 3~4명이어야 읽고 공유한다 |
| 3 | 두 팀 모두 보여주고 내 응원팀이 위(응원팀 선택은 FE) | 대비가 생기면 공유하고 싶어진다 |
| 4 | 흉 문구는 가볍게(선수를 깎아내리지 않음), 팀 문구·팁은 끝을 **응원으로 뒤집자**로 맺는다(데시벨 대결 연결). 부상·사생활·승부 단정 금지 | 응원 앱에서 선수 비하는 팬 반감. 흉 후에도 행동을 유도 |
| 5 | 결과는 (경기 날짜 KST, 생년월일)로 고정. 화면에 "재미로 보는 운세" 표기(FE) | 비교·공유가 가능하고 실제 출전으로 오해하지 않게 |
| 6 | 응답엔 생년월일 전체 대신 **`birth_year`만** (FE는 "98년생") | 개인정보 부담 감소 |
| 7 | 가짜 라인업(해시로 9명 뽑기)은 만들지 않는다. 문구도 "오늘 기운 좋은 선수"로 써서 출전 단정을 피한다 | 실제 출전과 다르면 거짓 정보 |
| 8 | 선수별 생일 보너스는 **이번 범위 밖**(여유 시) | 우선순위 낮음 |
| 9 | 코치·감독은 쓰지 않는다 | 선수만 후보 |

## 3. 계산 규칙

1. 선수 점수 `player_score = sha256(f"{birth_date}:{경기일}") % 100` (0~99). 같은 생일이면 같은 점수(사주식). 정렬 동점은 `kbo_id` 오름차순.
2. 등급(선수·팀 공통):

   | 점수 | 등급 | 이론 확률 |
   |---|---|---|
   | 88–100 | 대길 | 12% |
   | 68–87 | 중길 | 20% |
   | 43–67 | 소길 | 25% |
   | 23–42 | 소흉 | 20% |
   | 8–22 | 중흉 | 15% |
   | 0–7 | 대흉 | 8% |

   길 57% / 흉 43%. 응원 앱이라 길 쪽을 조금 더 둔다.
3. **팀 점수**: 후보 전체 점수의 평균을 그대로 쓰면 ~50 근처에 몰려 대부분 소길/소흉이 되고, 상위 N명 평균은 항상 대길이 된다. 그래서 평균을 정규분포 누적확률로 퍼센타일 변환한다: `team_score = round(100 × Φ((mean − 49.5) / (28.87/√n)))`. 결과가 0~100에 균등하게 퍼져 6단계가 위 확률대로 나온다. (`math.erf`로 계산)
4. 기운 좋은 선수 = 점수 상위 3명, 조심할 선수 = 점수 최하위 1명(그 등급이 **흉 계열일 때만**, 아니면 `null`).
   - 팀 등급과 선수 등급은 독립이다: 팀이 대흉이어도 "기운 좋은 선수"는 대길일 수 있다. 문구는 이 차이를 어색하지 않게 쓴다("팀 분위기는 무거워도 이 선수만큼은…").
5. 후보가 4명 미만이면 **기존 팀 시드(`pick_fortune`)로 폴백**, `lucky_players=[]`, `caution_player=null`, 등급은 그 점수에서 계산.
6. 문구 선택: 등급 풀에서 `sha256(날짜:팀id:등급)`으로 고르고, 두 팀이 같은 등급이면 id 큰 쪽을 한 칸 민다(같은 경기 두 팀 문구가 다르게).

## 4. 데이터

- 출처: `kbo_people.json` (koreabaseball.com, 수집일 2026-11-14) → `backend/app/seed/kbo_people_2026.json`로 복사. 10개 팀, 선수 1,043명, 생년월일 누락 0.
- 팀 코드→`Team.name`: LG→LG, HH→한화, SK→SSG, SS→삼성, NC→NC, KT→KT, LT→롯데, HT→KIA, OB→두산, WO→키움.
- `Player` 테이블: `id, kbo_id(UNIQUE), team_id(FK), name, position, back_number(null), birth_date`. 선수만 적재.
- 시드는 `seed/players.py`의 `seed_players`, `init_db` 끝에서 호출(kbo_id로 upsert).
- 문구 시드: `backend/app/ai/fortune_grades.json` — 등급별 팀 문구 8·팁 8·선수 한 줄 10. 기존 `fortune_seed.json`은 폴백용.

## 5. API (필드 추가만, 호환 유지)

`GET /matches/{id}/fortune?team_id=` 응답에 추가: `grade`, `lucky_players[]`, `caution_player`.
선수 항목: `{kbo_id, name, position, back_number, birth_year, grade, luck_score, one_liner}`. 스키마가 바뀌므로 push 후 FE가 `bash scripts/generate-client.sh`.

## 7. 남은 위험

- 후보가 1군이 아닐 수 있다(2군 일부 혼입). 1군 엔트리 데이터가 생기면 `is_candidate`만 바꾼다.
- 시즌 중이면 매일 1군 등록 변동이 있다. 이번엔 정적 스냅샷(2026-11-14)이다.
- 팀 이동·신규 선수는 데이터를 다시 받아 `kbo_people_2026.json`을 교체하고 `prestart.sh`를 돌리면 upsert된다.
